How the sync actually works

Every stage of an Airtable → Webflow run, in order, with the code that does it and the exact file and line to open.

01The 60-second version

Airtable is the source of truth. Webflow receives whatever Airtable says. The hard part is not writing things that have not changed — that is what the ledger exists for.

There are two separate Cloudflare Workers. They share storage but deploy independently.

syncwa-webNext.js dashboard
UI + API routes
→
syncwa-jobsCloudflare Queue
one queue, 3 job types
→
syncwa-enginequeue consumer
+ cron + WebSocket
→
SyncConnectionDurable Object
one per connection

The dashboard only ever produces jobs. The engine consumes them and owns all upstream API calls.

Why two Workers?

A Next.js request has a lifecycle; a 20,000-row sync does not fit inside one. Splitting them means the dashboard stays instant and the engine can take as long as it needs, one small job at a time.

What lives where

StoreHoldsWhy there
KV SYNC_KVConnection config, encrypted API tokens, cached schemasRead-heavy, rarely written, eventual consistency is fine
DO SYNC_DOThe per-record ledger, run state, logsNeeds atomic read-modify-write. KV cannot do this.
R2 MEDIARehosted Airtable attachmentsAirtable's own URLs expire in hours
Queue SYNC_QUEUEJobs in flightRetries, backoff, durability between steps
The one idea to hold onto

Every record is hashed. The hash is stored. On the next run the record is hashed again — if the hash matches, no Webflow call happens at all. On a table where 10 rows changed out of 5,000, the run makes 10 writes, not 5,000.

Scopes you actually need

Webflow: CMS read and write, plus Sites: read. The Sites scope is easy to miss — verify() calls GET /v2/sites, so without it saving fails immediately with an error message that only mentions CMS.

What the route does — and does not do

It validates and enqueues. No Airtable call, no Webflow call, no DO write. The run does not exist yet when the HTTP response returns.

app/api/connections/[id]/sync/route.ts:26–49
if (state?.status === "running") {
  // Without a staleness escape a genuinely stuck run would block every
  // future manual sync forever. Taking over is safe: each job checks
  // `state.runId` and the superseded chain abandons itself.
  const stuckFor = Date.now() - Date.parse(state.startedAt);
  if (stuckFor < STUCK_RUN_MS) throw new HttpError(409, "A sync has been running…");
}

if (mode === "incremental" && !state?.cursor) {
  throw new HttpError(400, "No previous successful run to be incremental against.");
}

const runId = crypto.randomUUID();          // ← minted HERE, in the dashboard
await env.SYNC_QUEUE.send({ type: "sync.start", connectionId: id, runId, mode });

Why “taking over” a stuck run is safe

Run A died mid-chain. The DO still says running, runId: A. After 30 minutes you are allowed through, and run B begins:

DO state: runId = A
sync.start(B) → beginRun overwrites
DO state: runId = B
stale sync.page(A, 4) arrives
state.runId !== job.runId→ return. Chain A dies silently.

That guard appears twice: worker/index.ts:109 and worker/index.ts:281

No work is lost

The ledger is keyed by record, not by run. A's committed records are already stored with their hashes, so B's claim() returns skip for every one. B resumes where A stopped.

Two real gaps

Paused connections accept syncs that never run. The sync route has no paused check, but handleStart returns silently at worker/index.ts:87. You get 200 {ok:true} and “Queued a full sync” — and nothing happens, not even a log line.

Credentials are not checked until page 0. handleStart never calls getCredentials, so a missing token lets the run start, log “sync started”, then fail six retries later.

05The job chain

A run is not one long task. It is a chain of small jobs, each of which enqueues the next only after it has committed.

sync.startopen the run
→
sync.page 0100 records
→
sync.page 1100 records
→
…until no offset
→
sync.finalizeorphans + close

All three types share one queue, syncwa-jobs, discriminated by job.type.

Why a chain instead of a loop

  • No memory ceiling. No invocation ever holds more than 100 records.
  • Every step is individually retryable. Page 7 failing retries page 7, not the whole table.
  • Naturally sequential. Page N+1 does not exist until page N committed.

The dispatch

worker/index.ts:331–340no default — the union is closed, so TS proves exhaustiveness
switch (job.type) {
  case "sync.start":    return handleStart(env, job);
  case "sync.page":     return handlePage(env, job);
  case "sync.finalize": return handleFinalize(env, job);
}

Queue configuration

worker/wrangler.jsonc:33–42
{
  "queue": "syncwa-jobs",
  "max_batch_size": 5,       // up to 5 jobs per invocation
  "max_batch_timeout": 5,    // …or after 5s
  "max_concurrency": 1,      // ONE invocation at a time, queue-wide
  "max_retries": 5,
  "dead_letter_queue": "syncwa-dlq"
}
The scaling constraint

max_concurrency: 1 is one lane for the entire queue, not one per connection. Connection B's sync waits behind all of connection A's pages. That is deliberate — it is what keeps you under both APIs' rate limits — but it is the first thing you will hit as connections multiply. The fix is a queue per connection, not raising concurrency.

syncwa-dlq has no consumer

Almost nothing reaches it: worker/index.ts:376–405 catches errors itself and always ack()s. Only an invocation that dies (CPU limit, OOM) produces a dead letter. When that happens the chain simply stops — the run sits at running until the 30-minute stuck threshold, with nothing logged. Adding a DLQ consumer that calls finishRun with an explanation is ~15 lines.

07The ledger — SyncConnection Durable Object

One instance per connection. This is the piece KV cannot do.

Why a Durable Object at all

Deciding whether a record needs writing is a read-modify-write against per-record state. With KV, two concurrent jobs could both read “no Webflow item exists yet” and each create one — a duplicate, permanently. A DO gives strongly consistent storage and single-threaded execution per connection, so claim is atomic by construction.

How the instance is addressed

worker/index.ts:57–59
function stubFor(env, connectionId) {
  return env.SYNC_DO.get(env.SYNC_DO.idFromName(connectionId));
}
  • idFromName() is a local hash — no network. The connection UUID always maps to the same 64-hex id.
  • .get() returns a stub. Nothing is instantiated until the first method call.
  • Both Workers reach the same instance, because the dashboard's binding carries "script_name": "syncwa-engine" wrangler.jsonc:44–46.

To print an instance id: this.ctx.id.toString(); this.ctx.id.name gives the connection id back.

09Finalize & orphan cleanup

An orphan is a ledger entry this run never saw in Airtable — i.e. the record was deleted upstream.

worker/index.ts:283–286the guard that prevents catastrophe
// Orphan detection compares "seen by this run" against the whole ledger, so
// it is only sound after a full pass. An incremental run sees a subset by
// design and would wrongly archive everything it skipped.
if (connection && job.mode === "full" && connection.deleteBehavior !== "ignore") {
Read this twice

Without job.mode === "full", an incremental run — which deliberately looks at only recently-modified records — would treat every record it did not fetch as deleted and archive the entire collection.

How orphans are found

listOrphans worker/sync-connection.ts:298–322 walks the at: prefix and returns entries where lastSeenRun !== runId. Remember that claim() stamps lastSeenRun on every record it sees — changed or not — which is exactly what makes this work.

The cleanup loop

for (;;) {
  const orphans = await stub.listOrphans(job.runId, ORPHAN_BATCH);   // 100
  if (orphans.length === 0) break;

  const removed = [];
  for (const orphan of orphans) {
    try {
      connection.deleteBehavior === "delete"
        ? await webflow.deleteItem(collectionId, orphan.webflowItemId)
        : await webflow.archiveItem(collectionId, orphan.webflowItemId);
      removed.push(orphan.recordId);
    } catch (error) { logs.push({ level: "error", … }); }
  }

  // Only forget records we actually dealt with, so failures are retried
  // by the next full run instead of being silently dropped.
  await stub.forget(removed);
  if (removed.length === 0) break;      // ← prevents an infinite loop
}

10Incremental mode & the cursor

run starts at 10:00:00
…pages run for ~4 minutes…
finishRun at 10:04:12success
cursor = startedAt − 60s
cursor = 09:59:00not 10:04:12

The cursor is anchored to when the run started, minus a 60-second overlap.

Why minus 60 seconds

Two hazards, one fix worker/sync-connection.ts:41–45:

  • Clock skew between Cloudflare and Airtable.
  • Edits made mid-run. A record edited at 10:02 while page 3 was processing might already have been read at 10:01. Anchoring to start minus overlap guarantees the next run re-examines it.

Re-examining is cheap: the hash will match if nothing really changed, so it costs a skip, not a write. Over-fetching is safe; under-fetching loses data.

The Airtable filter

lib/airtable.ts:136–149
// LAST_MODIFIED_TIME() with no arguments tracks every field on the record,
// so an incremental run needs no dedicated "last modified" column.
//
// CREATED_TIME() is OR'd in because Airtable returns BLANK for
// LAST_MODIFIED_TIME() on records that were created and never edited
// afterwards — a bulk paste or import. Without this, freshly added rows
// would be invisible to every incremental run.
url.searchParams.set("filterByFormula",
  `OR(IS_AFTER(LAST_MODIFIED_TIME(), '${modifiedAfter}'), ` +
  `IS_AFTER(CREATED_TIME(), '${modifiedAfter}'))`);
Hard-won detail

That OR(…CREATED_TIME…) is not defensive padding. Without it, records added by import would never sync — the single most likely “why is my row missing” bug in the whole system.

The cron scheduler

worker/index.ts:414–443runs every 5 minutes
for (const connection of connections) {
  if (connection.paused || !connection.schedule.enabled) continue;

  if (state.status === "running") {
    if (now - startedAt < STUCK_RUN_MS) continue;      // 30 min
  }
  if (lastSuccess && now - lastSuccess < intervalMs) continue;

  // Without a cursor there is nothing to be incremental against, so the
  // first scheduled run is a full pass.
  const mode = state.cursor ? "incremental" : "full";
  await env.SYNC_QUEUE.send({ type: "sync.start", connectionId, runId: crypto.randomUUID(), mode });
}
Duplicated constant

STUCK_RUN_MS is defined twice — worker/index.ts:41 and api/connections/[id]/sync:10 — because the two Workers share no module. If one drifts, cron will take over runs the UI still refuses to.

if (allowedOrigin && request.headers.get("origin") !== allowedOrigin) {
  return new Response("Origin not allowed.", { status: 403 });
}

const claims = ticket ? await verifyTicket(env.ENCRYPTION_KEY, ticket) : null;
if (!claims) return new Response("Invalid or expired ticket.", { status: 401 });

return stubFor(env, claims.c).fetch(request);

Hibernation is the point

worker/sync-connection.ts:69–90
/**
 * `acceptWebSocket` rather than `server.accept()` opts into hibernation: the
 * Durable Object can be evicted from memory while the socket stays open, and
 * is only woken when there is something to deliver. An idle dashboard tab
 * therefore costs nothing, which is the whole point of dropping the poll.
 */
this.ctx.acceptWebSocket(server);
// Send a snapshot immediately so the UI paints without waiting for a change.
server.send(JSON.stringify(await this.snapshot()));

What triggers a push

broadcast() is called at the end of claim, commit, forget, appendLogs and reset. Since beginRun and finishRun both log, run start and finish are covered too.

The browser side

  • Reconnect: 3s after a close, 5s after a ticket failure.

The retry decision

const retryable =
  error instanceof FatalSyncError ? false
  : error instanceof ApiError    ? error.retryable
  : true;                        // unknown → assume transient

if (retryable && message.attempts < 5) {
  message.retry({ delaySeconds: Math.min(300, 2 ** message.attempts * 5) });
  continue;
}

// Out of retries, or a permanent failure. Close the run out with the
// error so the dashboard shows why instead of a run stuck at "running".
await stubFor(env, body.connectionId).finishRun(body.runId, errorMessage(error));
message.ack();
Why every path ends in ack()

Recording the failure on the run is more useful than parking a message in a queue nobody watches. The handler's own ceiling (attempt 5) is reached before the platform's max_retries, so the normal failure path never produces a dead letter.

Error messages carry the upstream body

function errorMessage(error) {
  if (error instanceof ApiError) return `${error.message}${error.body ? ` — ${error.body}` : ""}`;
  return error instanceof Error ? error.message : String(error);
}

And describeApiError lib/http.ts:29–52 unwraps Airtable's and Webflow's structured JSON errors. A canned “check your scopes” string would send you hunting the wrong problem.

export class Pacer {
  private last = 0;
  constructor(private readonly minIntervalMs: number) {}

  async wait() {
    const elapsed = Date.now() - this.last;
    if (elapsed < this.minIntervalMs) await sleep(this.minIntervalMs - elapsed);
    this.last = Date.now();
  }
}
The Pacer is per-client-instance

A new WebflowClient is constructed in every handlePage invocation, so its last timestamp resets each job. What actually keeps the global rate safe is max_concurrency: 1 on the queue — only one job runs at a time. If you ever raise that, the pacing guarantee disappears with it.

Rough throughput

Webflow is the bottleneck at ~54 writes/minute. A first full sync of 1,000 new records takes roughly 18–20 minutes. The second run over the same unchanged table takes seconds — every record resolves to skip and makes no Webflow call at all.

Why this replaced echo suppression
lib/kv.ts:89–95
/*
 * Echo suppression used to live here as a `suppress:{conn}:{item}` marker with
 * a 60-second TTL. It is gone: KV writes take up to 60 seconds to propagate,
 * so the marker could be invisible at exactly the moment it was needed. Echo
 * detection is now the per-field base in the ledger, where an echo equals base
 * and is therefore not a change at all.
 */

A timing hack was replaced by a correctness property. An echo of our own write equals the base by definition, so it cannot register as a change no matter how the timing falls.

Field classes

lib/compare.ts:25–35

  • Bidirectional — PlainText, Email, Phone, Link, Number, Switch, DateTime, Option, Color. These canonicalise identically from both sides, so a Webflow edit is detectable.
  • Airtable-owned (push-only) — RichText, Image, MultiImage, File. Markdown becomes HTML and attachments become R2 URLs; there is no way to compare back. Their base tracks only the Airtable side, so an Airtable edit is still detected but a Webflow edit is never mistaken for one.

The Option case is the clearest illustration: Airtable gives a choice name, Webflow stores an option id. canonicalFromWebflow compare.ts:84–90 resolves the id back to its name and normalises both, so “unchanged” genuinely means unchanged.

Backwards compatible by design

base is optional on LedgerEntry types.ts:199–203: “Absent on entries written before ledger v2. Treated as unknown, which makes the next successful write populate it. No migration job needed.” And diffField treats a missing base as “never synced”, not as disagreement.
